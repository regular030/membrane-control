# Controller protocol version 1

115200 baud, 8N1, no hardware flow control. UTF-8 newline-delimited JSON. Maximum body size 8192 bytes excluding the newline, maximum 32 steps. A line contains one complete object. Reject malformed data without changing outputs. Reject invalid UTF-8, unpaired Unicode surrogates, embedded NUL characters, non-finite numbers, unknown valve counts, invalid schema versions and out-of-range values. Strings use standard JSON quoting and escaping.

Requests contain `v: 1`, a positive unsigned 32-bit integer `id` and `cmd`. Request IDs correlate responses; a write to the serial port is not an acknowledgement. A hello requires a matching `hello` response; other commands require a matching `ack` or `error` response. Boolean IDs are invalid.

Commands: `hello`, `heartbeat`, `load_recipe` (with `recipe`), `start`, `stop`, `manual` (with `valves`, `pump_percent`), `clear_fault`. Stop is accepted even when no recipe is loaded or a fault is latched. Manual operation is rejected during a recipe. A heartbeat never clears a fault or restarts a run.

Hello response:

```json
{"v":1,"id":1,"type":"hello","ok":true,"device":"basu-membrane-control","protocol_version":1,"firmware_version":"0.1.3","valve_count":7,"hardware_verified":false,"simulation":true}
```

Command response: `{"v":1,"id":2,"type":"ack","ok":true}` or `{"v":1,"id":2,"type":"error","ok":false,"error":"description"}`.

The desktop treats stop as an acknowledged transaction. It blocks new operations while stop is pending and records a user-stopped run only after the matching successful stop acknowledgement. Repeated stop clicks do not extend the three-second response deadline. A rejected, unsendable or unacknowledged stop latches a fault and closes the controller connection, withdrawing heartbeats so the firmware watchdog can stop outputs. A successful stop does not clear an existing fault.

Manual commands also block new operations until acknowledged. Stop cancels a pending manual operation. Acknowledgement confirms acceptance of a command, not physical valve movement. The desktop requires fresh telemetry before starting a run or sending manual controls.

Telemetry is unsolicited at approximately 4 Hz:

```json
{"v":1,"type":"telemetry","uptime_ms":1000,"state":"idle","step_index":-1,"cycle":0,"remaining_s":0,"valves":[false,false,false,false,false,false,false],"pump_percent":0,"pressure_psi":null,"flow_ml_min":null,"pump_feedback_v":null,"fault":null,"hardware_verified":false,"simulation":true}
```

`valves` are commanded logical states, not physical position feedback. `pump_feedback_v` is a signal voltage, not measured flow. Missing measurements are JSON null. The UI must not carry a last-known value forward as current after a timeout.

`uptime_ms` is required and must be an unsigned 32-bit integer. The desktop accepts normal counter rollover. An implausible uptime jump, including most resets, closes the link and marks an active run as faulted. An unexpected return to idle before the recipe could have finished also faults the run. Uptime is a diagnostic rather than a unique boot-session identifier. A change in the connected controller's simulation or hardware-verification flags faults the connection. Reconnect never resumes a run automatically.

Recipe shape:

```json
{"schema_version":1,"name":"Example","description":"Demonstration only","hardware_approved":false,"repeat":1,"sample_interval_s":1.0,"require_balance":false,"steps":[{"name":"Observe","duration_s":10.0,"valves":[false,false,false,false,false,false,false],"pump_percent":0.0}]}
```

Repeat is 1-100; each duration is 0.1-86400 seconds; cumulative repeated duration is at most 604800 seconds. Pump percent is 0-100. Each state must explicitly specify seven booleans. Recording interval is 0.1-3600 seconds. Names are at most 64 characters and 80 UTF-8 bytes, with no control characters. Descriptions are at most 512 characters and 1000 UTF-8 bytes. No executable expressions or scripts are accepted in recipes.

Dry-run firmware and the desktop simulator explicitly report `simulation: true`. Physical firmware requires a separately verified compiled board profile and a hardware-approved recipe. A desktop checkbox cannot override an unverified physical board profile. Outputs default inactive and firmware remains idle on startup; switching hardware must independently establish appropriate safe states.

An active controller with no valid heartbeat for 3000 ms stops and latches a communication fault. The desktop sends heartbeats every 500 ms, treats telemetry older than 2 seconds as stale, and never resumes automatically after reconnect. Pressure protection is local to physical firmware. Balance loss is enforced by the desktop for recipes requiring it; firmware heartbeat is withdrawn if the desktop cannot issue a stop.
