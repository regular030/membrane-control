# Controller protocol version 1

115200 baud, 8N1, no hardware flow control. UTF-8 newline-delimited JSON. Maximum body size 8192 bytes excluding the newline, maximum 32 steps. A line contains one complete object. Reject malformed data without changing outputs. Reject invalid UTF-8, unpaired Unicode surrogates, embedded NUL characters, non-finite numbers, unknown valve counts, invalid schema versions and out-of-range values. Strings use standard JSON quoting and escaping.

Requests contain `v: 1`, a positive unsigned 32-bit integer `id` and `cmd`. Request IDs correlate responses; a write to the serial port is not an acknowledgement. A hello requires a matching `hello` response; other commands require a matching `ack` or `error` response. Boolean IDs are invalid.

Commands: `hello`, `heartbeat`, `load_recipe` (with `recipe`), `start`, `stop`, `manual` (with `valves`, `pump_percent`), `manual_valves` (normal six-valve mode, described below), `clear_fault`. Stop is accepted even when no recipe is loaded or a fault is latched. Manual operation is rejected during a recipe. A heartbeat never clears a fault or restarts a run.

Hello response:

```json
{"v":1,"id":1,"type":"hello","ok":true,"device":"basu-membrane-control","protocol_version":1,"firmware_version":"0.1.16","pump_command_source":"gp8403","valve_count":7,"hardware_verified":false,"simulation":false,"valve_control_ready":true,"manual_valve_count":6,"manual_valve_ids":[1,2,3,4,5,7],"valve_bits":[0,1,2,3,5,6]}
```

Command response: `{"v":1,"id":2,"type":"ack","ok":true}` or `{"v":1,"id":2,"type":"error","ok":false,"error":"description"}`.

Firmware 0.1.13 adds optional HELLO diagnostic `pump_command_source`, either
`gp8403` or `pwm_converter`, describing its compiled command source. This is
configuration metadata, not converter detection or measured analog voltage.
Older clients/firmware can omit it. A dry-run image never operates either source.
The PWM backend holds the separate pump stop contact during a command change
and its reviewed nonblocking settling interval. RUN activation is permitted only
after the current firmware safety tick. `pump_percent` remains the commanded
percentage, not a promise that the motor is already running or at that speed.

A verified physical profile can advertise `manual_pump_profile` in HELLO.
Its `max_percent` is the profile's upper pump command and `valves` is its
required seven-slot valve array. The desktop uses that valve array for a
direct manual pump command. Firmware can accept that command while idle
or while manual valves already match the required array. Pressure validity,
the cutoff and the command lease apply throughout manual operation.

A PWM profile can opt into a bounded low-pressure manual start by advertising
`manual_pump_profile.pressure_startup_ms` in HELLO (at most 1000 ms with the
RUN contact commanded closed). When the current native ADC sample falls below
the calibrated range, telemetry can report `pressure_startup: "available"`.
A `manual` command with `allow_pressure_startup: true` can then start at the
profile's required valve path. `pressure_startup: "active"` covers staging
and the brief window before the first valid pressure sample. The cutoff applies
on every valid sample. A stale or otherwise invalid sample, an expired window,
or loss of the command lease stops the pump. A valid sample ends the window
for that start. Optional `pressure_adc_mv` gives the fresh pin voltage, while
`pressure_psi` remains null outside the calibrated range. Recipe starts still
require a valid pressure sample.

Commissioned physical firmware can also report optional pump fields in
telemetry. `pump_run_contact_commanded` is the controller's requested RUN
contact state. `pump_feedback_v` is the calibrated drive command output
voltage. With a commissioned tach input, `pump_rpm` reports measured
rotational speed for the last completed measurement window. `pump_tach_status`
is `waiting`, `reading_received`, `no_pulses`, or `unavailable`. Zero RPM
with `no_pulses` means the counter saw no edges during the window. A lost
tach signal can also give this result. Older or factory firmware can omit
the optional contact and tach fields.

Firmware 0.1.14 adds optional HELLO diagnostics: `controller_mode` (`dry_run` or
`physical`), `hardware_status` (null when ready, otherwise a bounded reason),
and `sensor_inputs`. The latter uses keys `pressure`, `flow`, `pump_feedback`,
each containing `source` (`disabled`, `native_adc1`, `ads1115`), explicit
`calibration_verified`, and the selected `pin` or `channel` where applicable.
These report compiled configuration, not detected sensor presence.

Telemetry may include `sensor_status` with the same three sensor keys and
values `simulated`, `not_configured`, `profile_locked`, `hardware_unavailable`,
`uncalibrated`, `out_of_range`, `stale` or `reading_received`. Status never
substitutes for a numeric reading or opens an acquisition/control gate. Older
packets omit it. The desktop ignores malformed optional metadata, clears stale
reasons on fresh legacy telemetry, and gives valid numbers (including zero),
disconnection and transport freshness precedence over diagnostic labels.

## Factory sensor voltage check, 0.1.18

Factory physical firmware advertises optional `sensor_test_available: true` in
HELLO. While idle, `read_sensor_inputs` reads the fixed, protected ADC pins once.
The matching ACK includes `adc_pin_mv` with integer millivolt values for
`pressure` (GPIO34), `flow` (GPIO36), and `pump_feedback` (GPIO39).
Dry-run and custom profiles reject the request. The diagnostic changes no
outputs or calibration and does not supply normal telemetry or a pressure
interlock value.

Factory physical 0.1.19 also publishes `adc_pin_mv` with the same fields
in periodic telemetry while idle or using manual valves. Old firmware, dry run,
commissioned profiles and fault states may omit it. Clients clear the displayed
diagnostic values when the field disappears or telemetry goes stale. Normal
ESP32 HELLO may include a `reset_reason` token for its last recorded boot.

## Normal manual valves, 0.1.16

The six installed valves are V1-V5 and V7, mapped to shift-register bits
0, 1, 2, 3, 5 and 6 respectively. Their coils are active HIGH.
Normal physical firmware advertises `valve_control_ready: true`,
`manual_valve_count: 6`, `manual_valve_ids: [1,2,3,4,5,7]` and
`valve_bits: [0,1,2,3,5,6]`. The ID and bit arrays correspond element by element;
both explicit arrays are required to establish this manual capability. Count
alone or old sequential metadata cannot enable it. This capability is
independent of full pump/experiment `hardware_verified` and requires no sensor
readings or runtime approval flags. `valve_count: 7` continues to describe the
legacy wire-array width, so older recipe/data formats remain readable.

`manual_valves` accepts only `valves`, an array of seven strict booleans. The
slots retain physical valve-number order: indices 0-4 control V1-V5, index 5
is the absent V6 and **must be false**, and index 6 controls V7. The desktop
maps the six named operator choices using `manual_valve_ids`; it must not pack
V7 into the V6 slot. A pump field is
not accepted. Active state is `manual_valves`, pump_percent is always0, and
unused bit 4 and bits 7-15 remain LOW. For example, V7 alone is requested by
`{"v":1,"id":2,"cmd":"manual_valves","valves":[false,false,false,false,false,false,true]}`.
Commands persist until changed, Stop, Hello/reconnect,
fault or the three-second heartbeat timeout. Only idle/manual_valves can accept
this command; Stop first when changing from pump-manual or recipe operation.

The shipped normal profile initializes only the known595 relay pins for this
capability. It does not acquire unconfigured sensors or initialize a pump DAC,
PWM output or contact. Full pump/experiment commands retain their existing
requirements. If an already configured full driver owns compatible relay I/O,
the same hardware owner is reused. Telemetry includes valve_control_ready and
the existing seven commanded valve slots, with absent V6/index 5 false and
V7/index 6 available. V7 must not be renumbered to close the gap.

Starting in 0.1.20, normal firmware may add `manual_valves_receipt_id` to
`manual_valves` telemetry. It is the positive request ID of the last valve
command applied to the outputs in that mode. A fresh frame with that exact
pending ID and the requested valve bits can confirm the command if its
ordinary ACK was lost. A matching state alone is insufficient. This does not
confirm physical valve position, apply to Stop, or replay an actuator command.

The desktop treats stop as an acknowledged transaction. It blocks new operations while stop is pending and records a user-stopped run only after the matching successful stop acknowledgement. Repeated stop clicks do not extend the three-second response deadline. A rejected, unsendable or unacknowledged stop latches a fault and closes the controller connection, withdrawing heartbeats so the firmware watchdog can stop outputs. A successful stop does not clear an existing fault.

Manual commands also block new operations until acknowledged. Stop cancels a pending manual operation. Acknowledgement confirms acceptance of a command, not physical valve movement. The desktop requires fresh telemetry before starting a run or sending manual controls.

Telemetry is unsolicited at approximately 4 Hz:

```json
{"v":1,"type":"telemetry","uptime_ms":1000,"state":"idle","step_index":-1,"cycle":0,"remaining_s":0,"valves":[false,false,false,false,false,false,false],"pump_percent":0,"pressure_psi":null,"flow_ml_min":null,"pump_feedback_v":null,"fault":null,"hardware_verified":false,"simulation":true}
```

`valves` are commanded logical states, not physical position feedback. `pump_feedback_v` is a signal voltage, not measured flow. Missing measurements are JSON null. The UI must not carry a last-known value forward as current after a timeout.

`uptime_ms` is required and must be an unsigned 32-bit integer. The desktop accepts normal counter rollover. An implausible uptime jump, including most resets, closes the link and marks an active run as faulted. An unexpected return to idle before the recipe could have finished also faults the run. Uptime is a diagnostic rather than a unique boot-session identifier. A change in the connected controller's simulation or hardware-verification flags faults the connection. Reconnect never resumes a run automatically.

Recipe shape:

```json
{"schema_version":1,"name":"Example","description":"Demonstration only","hardware_approved":false,"repeat":1,"sample_interval_s":1.0,"require_balance":false,"steps":[{"name":"Observe","duration_s":10.0,"valves":[false,false,false,false,false,false,false],"pump_percent":0.0}]}
```

Repeat is 1-100; each duration is 0.1-86400 seconds; cumulative repeated duration is at most 604800 seconds. Pump percent is 0-100. Each state must explicitly specify seven booleans. Recording interval is 0.1-3600 seconds. Names are at most 64 characters and 80 UTF-8 bytes, with no control characters. Descriptions are at most 512 characters and 1000 UTF-8 bytes. No executable expressions or scripts are accepted in recipes.

Desktop recipe files may also contain `desired_flow_ml_min` (finite number,
0-1000000, default 0 for older files). This is comparison and recording metadata,
not a flow-control command. The desktop omits it from the wire recipe above;
firmware continues to execute explicit per-step pump percentages.

Dry-run firmware and the desktop simulator explicitly report `simulation: true`. Physical firmware requires a separately verified compiled board profile and a hardware-approved recipe. A desktop checkbox cannot override an unverified physical board profile. Outputs default inactive and firmware remains idle on startup; switching hardware must independently establish appropriate safe states.

An active controller with no valid heartbeat for 3000 ms stops and latches a communication fault. The desktop sends heartbeats every 500 ms after a valid handshake and telemetry, withholds them during Stop or a fault, treats telemetry older than 2 seconds as stale, and never resumes automatically after reconnect. Pressure protection is local to physical firmware. Balance loss is enforced by the desktop for recipes requiring it; firmware heartbeat is withdrawn if the desktop cannot issue a stop.
